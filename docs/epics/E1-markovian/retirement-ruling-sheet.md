Each row carries: the claim ID and its **current register status** (from `docs/epistemic/CLAIMS.md`,
parsed at HEAD on 2026-08-03), the **family reason** (one line, copied from §2 — not re-argued
per row), **what is lost if it is retired**, and an empty `RULING:` column.


RECOMMEND column filled by T324; the RULING column remains empty for Orcha. Retirement is a disposition marker (`RETIRED`) — the row text and history stay in the register.

### How "what is lost" was cross-checked

Two mechanical checks, both reported per row, plus a judged flag:

- **In-register dependents** — parsed from the `dependents` column of the retiring row in
  `CLAIMS.md`, then filtered to those whose own `tree` cell is **not** `RETIRED` (i.e. still
  live). The edge kind (`e:` evidenced-by / `d:` derives-from / untyped / dependents-only) is
  read from the *live* row's `depends-on` column. A `dependents-only` edge means the retiring
  row's `dependents` column names the live row, but the live row's `depends-on` does not name
  the retiring row — an asymmetric register entry that breaks nothing on retirement.
- **External `docs/` citations** — `grep` for the claim ID across every `docs/**/*.md` except
  `CLAIMS.md`, `register-tree-map.md`, and this sheet. These are counted and three example paths
  shown. A high count usually means historical narrative (PROGRESS.md, ADRs), not a live
  logical dependency; it is reported so the human can see how widely the row is referenced.
- **⚑ sole-evidence flag (judged from the mechanical data)** — where a retiring row is the
  `e:` (evidenced-by) source for a live row whose status is still believed (PROVEN / CLAIMED /
  UNTESTED / MEASUREMENT, i.e. not FALSE-AS-SCOPED), it is flagged. Per the T318 bar, such a row
  is **not a retirement candidate** until the live row's `depends-on` is re-pointed; retiring
  it silently would leave a still-believed claim with a dangling evidence edge. Eight rows are
  so flagged.

### What is the issue

About one third of the register (116 / 323 rows) maps to no requirement-tree node in `register-tree-map.md`. They are ruleset-choice foreclosures, old-artifact diagnostics, player-side claims, process rules, design rationale, and crisis-era framings. Under DIRECTION §1, a row that maps nowhere is not part of the theorem's evidence chain. Keeping them in the live register creates audit load (claimlint, the battery, and every reverification pass must account for them), carries false epistemic weight (a PROVEN/CLAIMED status on a non-requirement reads as a theorem result), and feeds the C2/C3/C4 debt by letting old-scope statements masquerade as fresh-start claims. The issue is not that the history is wrong; it is that the live register cannot tell history from hypothesis.

### Impact of retiring vs keeping

**Retiring** means changing the `tree` cell to `RETIRED` (a disposition marker), not deleting the row. The row text, status history, and external citations remain in `CLAIMS.md` and in `docs/`. The register-tree-map already carries `RETIRED` for every row proposed here. Reversibility is therefore built in: if a future requirement node is created that a retired row genuinely evidences, the row can be re-mapped. Retirement removes 108 rows from the live theorem-evidence surface, shrinking the audit domain to the 207 mapped rows and the documented gaps in `register-tree-map.md` §5.

**Keeping** the rows live means either (a) inventing tree nodes for 116 non-requirements, which would bloat the theorem with player, process, and historical claims, or (b) leaving them unmapped, which reproduces exactly the ambiguity DIRECTION §1 is trying to close. It also preserves the risk that a future auditor treats a player-side or old-artifact measurement as a theorem premise, repeating the C2/C3/C4 confusion the project is unwinding.

The only cost of retiring is the nine edges that are not free: eight sole `e:` evidence rows must be re-pointed, and one `d:` derive edge (`4x4.COMPLETE-2026-07-21` → `GLOBAL.ADR0012-GATE`) must be re-pointed before the register status changes. These are listed per row in the RECOMMEND column.

### Is retirement better or worse for the project

**Retirement is better.** I recommend retiring **108** of the 116 rows and deferring **8** until their live dependents are re-pointed. I recommend keeping **0** rows: none of the 116 map to a current requirement-tree node or carry a concrete future-use burden that outweighs the cost of keeping them live. The deferred rows are not opposed to retirement; they are retirement candidates whose evidence edges need rewiring first. Once those nine edges are re-pointed, the full 116 should be retired.
