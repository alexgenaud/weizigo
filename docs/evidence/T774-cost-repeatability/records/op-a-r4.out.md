## 3. Checked and found SAFE

Each of these is a construct a careless reader would flag. None is a defect at HEAD.

- **`open(path, errors="replace")` — `token-capture.py:361`, `:490`.** Safe *as a flag*. It prevents one bad byte from aborting the whole read; the mangled lines then fail `json.loads` and land in the `bad` counter. The defect is the counter's invisibility (#5), not `errors="replace"` — removing the flag would trade a silent undercount for a total read failure, which is worse under the same rule.
- **`read_pi_session`'s missing-file path — `token-capture.py:354–355`:** `if not os.path.isfile(path): return {"ok": False, "reason": "session file missing: %s" % path}`. Correct: absent file ⇒ `ok=False` ⇒ `tools/runner:2270` builds a reason and leaves `tokens_in` at `None`. UNKNOWN, never 0. Same for `:359–360` on `OSError`. This is the brief's headline hazard and it is handled.
- **`--session <id>` instead of a path.** `_argv_session_path` (`tools/runner:1593`) matches the flag pair blindly, and pi accepts an id there — but `:2251–2253` resolves it against cwd to a path that does not exist, so it falls into the missing-file branch above. Degrades to UNKNOWN with a naming reason, never to 0.
- **`_write_run_record` — `tools/runner:526–551`.** Genuinely atomic: `tmp` write, `f.write("\n")`, then `os.replace(tmp, path)`, with tmp cleanup on `OSError`. The visible file is always either the complete old record or the complete new one. No torn-read window. (Its `except OSError` does not cover a `TypeError` from an unserialisable value, but every field written is `int`/`float`/`str`/`None`, so there is nothing to serialise badly.)
- **`peak_rss_mb = max(peak_rss.values())` — `tools/runner:3276`, max over PIDs rather than sum.** Not an undercount bug: this is the *defined* quantity, stated in the flag help at `:2479` `help="log per-member peak RSS on exit (default true)"` and in `_log_peaks`'s output at `:1445` `"[runner] peak RSS by PID:"`. A per-member peak is the right figure for a per-process cap check; summing concurrent peaks would be the wrong one.
- **`_descendant_pids_linux` / `_descendant_pids_ps` — `tools/runner:1027`, `:1055`.** Both seed the BFS with `stack = [root_pid]` and `pids.add(pid)` before extending, so **the direct child is included**, not just its descendants, despite the function names. CPU and RSS for the wrapped command itself are measured.
- **`recompute_harness_p95` — `tools/runner:1920–1996`.** The model citizen of this surface. It partitions the population explicitly (`census["unparseable"]`, `census["incomplete"]`, `census["killed_agent"]`, `census["bakeoff"]`), excludes each with `continue`, re-checks `if w is None` at `:1977` after the `exit` check, and reports `"n"` per family at `:1988`. A missing wall can never be absorbed as 0, and the denominator is published.
- **`parse_claude_envelope`'s total-parse-failure path — `token-capture.py:252`:** `return text, None, _empty_meta()`. `usage=None` ⇒ `tools/runner:2212` is false and `:2228` sets `"no claude usage envelope in output"`. A shape change degrades to UNKNOWN *and* passes the raw text through unchanged (`:225` `text = raw or ""`), so the lane's answer is never silently emptied.
- **The stream-json fallback keeping the last object — `token-capture.py:246–250`.** Correct for `--output-format stream-json`, where the usage envelope is the terminal `result` event; and it only runs when no whole-output parse succeeded (`if obj is None` at `:243`). It cannot shadow a correctly-parsed single-object envelope.
- **`extract_task` refusing a bare `T<id>` — `token-capture.py:456–465`.** Deliberately conservative: only `untracked/T(\d+)` and `claim\s+T(\d+)` match, so prose mentioning another task cannot capture the session. The docstring at `:459–461` states the rule and the code implements it.
- **`_json_output_lane` detecting by flag, not binary name — `tools/runner:1562–1573`.** A claude lane dispatched without `--output-format json` falls through to the pi branch and produces an UNKNOWN whose *reason text* is mislabelled ("pi/ollama lane") — but the reading itself is correctly absent. A wrong reason on a correctly-UNKNOWN row is a legibility problem, not a wrong reading, and I am not counting it as one.
- **token-backfill's append-only discipline — `token-backfill.py:150`, `:185–187`, `:203–216`, `:227`.** `have_reading` blocks any task with a dispatch-time reading; every retro row carries `"trusted": False` plus `supersedes_ts` naming the record it corrects; CONFLICT rows `continue` and are never appended. A retro scan cannot overwrite dispatch-time truth. (Its one real weakness is that `_is_reading` counts a silent zero as a reading — that is #11/#1, charged there, not here.)
- **`control()` — `token-backfill.py:240–272`.** A real null control (a task with a dispatch-time reading must produce no append) plus a real seeded-defect control (`canon_tag('stealth/ox-alpha') != 'ox-alpha'` ⇒ FAIL). It also prints `SKIP` rather than `pass` when the ledger has nothing to guard — it does not fake a green.
- **Degraded (no-identity) mode — `tools/runner:2661–2693`.** Six stderr lines announce it, including `:2686` naming the T515 rule, and `record_root = repo_root if not identity_degraded else None` at `:2693` makes the record and ledger writes no-op. Nothing wrong is recorded; the envelope parse still runs at `:2199` so the lane's text is not lost. A degraded run is *absent* from the cost comparison, not zero in it — and loudly so.
- **Heartbeat `None`-stripping — `tools/runner:651` `record = {k: v for k, v in record.items() if v is not None}`.** Cannot silently zero a token field: `tokens_in`/`tokens_out` are only inserted at `:648–650` under `if tokens_in is not None`, and `wall`/`cpu`/`rss_mb` are pre-converted to `None` by the `if … >= 0 else None` guards at `:643–645`, so the sentinel `-1` never reaches the file as a number.
- **`sum(peak_cpu.values())` across the tree.** Right shape, not a wrong-process read: `peak_cpu[pid] = max(peak_cpu.get(pid, 0.0), cpu)` at `:2991` keeps each pid's last cumulative reading even after it exits, so exited descendants still contribute. The loss is bounded by one poll interval per pid, plus pids that live entirely between polls — a resolution limit, not a wrong process. (Whether `ps -o time` double-counts reaped children is Q1 below.)
