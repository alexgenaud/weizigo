## 4. What this run establishes (and what it does not)

**Establishes.** The WZO2 4×4 *builder* reproduces its table across a two-day
gap and the intervening commits to its source. G3a no longer rests on one
unrepeatable run: "this artifact has property P" becomes "the *builder* produces
artifacts with property P".

Intervening commits between the prior build (T212, commit `144148c`,
2026-08-01) and the rebuild binary (`f25e615-dirty`, built 2026-08-03T02:24:49Z)
touching the builder's import closure (`oracle_v2_build.zig`, `exp6_solve.zig`,
`rules.zig`, `artifact2.zig`, `colex.zig`, `version`), verified by
`git log 144148c..f25e615 -- <files>`:

| commit | change | on the 4×4 builder's behavioral path? |
|---|---|---|
| `fd87f83` (T226) | `areaScore` moved into `rules.zig` as a runtime dispatcher; `exp6_solve.zig` delegates (`:211`) | yes — computation path |
| `7609420` (T226 A4.2/A4.3) | `neighborsRt` runtime dispatcher + tests in `rules.zig` | yes — computation path |
| `193fdc6` (T226) | `genericNeighbors` now delegates to `rules.neighborsRt` (`exp6_solve.zig:127`) | yes — computation path |
| `4a598b1` (T264) | version stamping: `version.banner` in the builder's stdout, manifest.json, `untracked/vNN` output diversion + VERSION counter | yes — but output plumbing only, not the table |
| `656c6d3` (T274) | WZO1 writer output-path diversion inside `exp6_solve.zig` `main()` (`:1535`-area) | no — `main()` is not called by the builder |
| `b475533` (T273) | Phase-2 kernel: `koAfterCapture`/`stateKey` added to `rules.zig` | no — new functions; `neighborsRt`/`areaScore` unchanged |

The brief named four intervening commits; the accurate count is **six commits
touching files in the builder's import closure**, of which four are on the
behavioral path (three of them T226's neighbours/area runtime delegation). The
claim is therefore *stronger* than the brief's "four": the neighbours/area
computation itself was re-delegated between the two runs and the bytes still
match.

Two corollaries, verified from source:

1. **T226's `genericNeighbors` delegation was behaviour-preserving on this
   path** — the 4×4 table (and per-sweep L/H change trace) is unchanged by the
   move to the runtime dispatchers.
2. **The artifact header carries no build stamp.** `artifact2.Header` is
   `{w, h, ko_bits, n_groups, n_entries, sha256}` only (32-byte hash of the data
   sections; `src/artifact2.zig:88-94`), and the builder zeroes the header hash
   slot before `buildFile` fills it (`src/oracle_v2_build.zig:479`). T264's
   sha/date/dirty banner reaches the log and manifest but **not the artifact
   bytes** — which is why byte-identity holds despite different binaries.

**Does NOT establish — and this record must not be read as if it did:**

1. **Nothing about the extracted kernel.** The builder imports `rules.zig`
   (via `exp6_solve.zig`) only for `neighborsRt` (`exp6_solve.zig:127`) and
   `areaScore` (`:211`). Its ko rule is its own — `apply_place4` computes
   `new_ko` inline with the `liberties == 1 and friendly == 0` shape test
   (`:886`-onward). The builder remains one of the divergent ko copies
   (GRAND-AUDIT §1b); this run neither validates T273's kernel nor shows the
   extraction was behaviour-preserving. Consistent with `b475533` adding new
   functions that the builder's path never calls.
2. **Nothing about value correctness (G3b).** Reproducibility is not
   correctness: a deterministic builder reproduces its bugs exactly. C-A1/C-A2
   and the kernel move generator remain what G3b needs.
3. **Nothing about the WZO1 artifacts** — different format, different lineage,
   not compared here.
