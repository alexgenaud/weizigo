## Command

```
tools/runner --rss-cap-mb 4096 --max-wall 14400 --max-cpu 0 --task-id DSPro/T184 -- \
  zig run -O ReleaseFast src/oracle_v2_build.zig
```

**Note:** `--max-cpu 0` was required — the default 3600s CPU ceiling killed the
first run during DTT computation (the builder needs ~65 min of CPU). The wall
ceiling at 14,400s (4h) is the correct budget; the CPU ceiling catches busy-spin
but this process is legitimately CPU-bound.

(`## Writing WZO2 artifact`). The process survived census, fixpoint, DTT, and
group/entry construction (~3231 MB seen in run 1) but the file_bytes allocation
(518 MB) plus the write buffer pushed past 4 GB. No `.wzo2` file was written.

## DTT truncation hazard assessment

**NO hazard.** `final_changes = 0` at sweep 10 (well before the 254 clamp).
All states resolved with finite DTT (FAR=0). The DTT value clamp (254) and
sweep cap (254) are not aliased — DTT converged cleanly at sweep 10 with zero
residual changes. The hazard described in `CODE.WZO2-UNRUN` paragraph (a) did
not materialize.

## G bracket assessment

G = 24,318,165 — exactly at the upper bound of the [23,802,969, 24,318,165]
prediction bracket (`4x4.G-CENSUS`). The upper bound is the legal position
count (OEIS A094777(4)). This means **every legal board position has at least
one entry in the compact list** — no reachable board is absent. This implies
the census reached every legal board position through some ko/passes
combination, which is a structural finding: the basic-ko state graph is
ergodic over the set of all legal boards.

The killer is the 1 GiB write chunk buffer (`CHUNK: usize = 1 << 30` at
`src/oracle_v2_build.zig:469`). The `writePositionalAll` likely copies the
full chunk, allocating an additional 1 GiB on top of the 518 MB file_bytes
and the ~2 GB of live data structures.
