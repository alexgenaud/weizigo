**The claim under audit** (as quoted in the EXP-16 brief):

> `Session.choose` in `src/gtp.zig` does table lookups only and never searches.

**Where the claim actually lives** (see "brief-accuracy findings" below): the
verbatim form is `docs/status/HANDOVER.md` §"Gotchas — read before you run
anything" (lines 61–63): *"`Session.choose` in `src/gtp.zig` never searches — it
is table lookups only. ADR-0013's closing line claiming the GTP player inherits
the finisher's fix is false; do not rely on it."*

## VERDICT: **VERIFIED**

`Session.choose` (`src/gtp.zig:184`) is a one-ply extremum over stored child
values plus deterministic fixed-work goban functions. It performs **no** call to
`solve`, `retro_solve`, `Exact`, the finisher, the arena evaluator, or any
search. Decisive structural fact: **`src/gtp.zig` does not import the solver at
all** — its only imports are `rules.zig`, `colex.zig`, `artifact.zig`,
`score.zig` (src/gtp.zig:55–58); `solve.zig` and `retro.zig` are unreachable
from the GTP player's `Session` code. A `grep` of the file for
`solve|Exact|retro|finisher|arena` hits only comments ("resolve fast",
"arena pipeline").

The function body's last statement is `return best.?;` (src/gtp.zig:225),
returning the extremum winner (or the early-game `best_move` override),
computed entirely from colex-keyed table reads. There is **no fall-back search
path**: UNDEF children are *skipped* in the same one-ply loop
(`if (v == UNDEF) continue;`, src/gtp.zig:201); if every move is skipped, the
pass candidate stands. KO_SENSITIVE nodes take the *identical* code path — the
extremum is computed and steered by anyway (that is the documented
`4x4.GTP-DEFECT`, not a hidden search). The table is never "cold": the full
artifact is loaded once at session start (`artifact.load`) and no lazy solving
exists.

## The function, verbatim

`Session.choose`, src/gtp.zig:184–226 (doc comment, not reproduced, spans
:152–183 and includes the honesty caveat that the extremum is well-defined only
on the chainable region):

```
184:         pub fn choose(s: *const S, side: i8) Choice {
185:             const maximizing = side > 0;
186:             const opp: i8 = -side;
187:             const opp_before = S.countColor(&s.pos, opp);
188:             const pass = Choice{
189:                 .cell = null,
190:                 .value = if (s.passes >= 1) R.area_score(&s.pos) else s.v1_from_table(&s.pos, -side),
191:                 .dtt = if (s.passes >= 1) 0 else 1,
192:                 .caps = 0,
193:             };
194:             var best: ?Choice = pass; // pass is a candidate
195:             var best_move: ?Choice = null; // best non-pass candidate (early-game effort)
196:             for (0..n) |p| {
197:                 if (s.pos[p] != 0) continue;
198:                 const child = R.pos_from_move(&s.pos, side, p) catch continue;
199:                 if (s.seen(&child)) continue; // positional superko
200:                 const v = s.v0(&child, -side);
201:                 if (v == UNDEF) continue; // unfilled slot (2-ko+): skip
202:                 const dt = s.dtt0(&child, -side);
203:                 const caps: u16 = opp_before - S.countColor(&child, opp);
204:                 const mv = Choice{ .cell = p, .value = v, .dtt = dt, .caps = caps };
205:                 best_move = S.pick(best_move, mv, maximizing);
206:                 best = S.pick(best, mv, maximizing);
207:             }
208:             // early game (own < area/4 AND total < area/2; 4 own / 8 total on
209:             // 4x4): if pass would be chosen, play the best move instead.
210:             if (best.?.cell == null) {
211:                 const area: usize = w * h;
212:                 const min_own: usize = area / 4;
213:                 const min_total: usize = area / 2;
214:                 var own: usize = 0;
215:                 var tot: usize = 0;
216:                 for (s.pos) |x| {
217:                     if (x == 0) continue;
218:                     tot += 1;
219:                     if ((x > 0) == (side > 0)) own += 1;
220:                 }
221:                 if (own < min_own and tot < min_total) {
222:                     if (best_move) |bm| return bm;
223:                 }
224:             }
225:             return best.?;
226:         }
```

**Shape notes (relevant to dependents, not to the verdict):** (a) when

## Calibration: the H5a dependency check (mandatory per brief)

EXP-9 (`docs/infra/dispatch/EXP-9.md`) §"The mitigation (with both D-3
corrections)" is the load-bearing consumer. Its design assumptions, checked
against this verdict:

1. **Cost model "…(~`2n` lookups; still cheap)."** — depends on `choose`'s
   extremum being reproducible by ~n+1 table reads at the node plus ~n+1 at the
   chosen child. VERIFIED sustains it exactly: choose is ~n `v0`/`dtt0` reads +
   fixed-work goban ops, so the A1/A2 checks double precisely the quantities
   choose already consumes. If choose searched, both the cost claim and the
   characterization of the check as "the one-ply Bellman identity" fail.
2. **A2 — "check the chosen child `C*` (the move `choose` would return)."** —
   requires `C*` to be computable by the mitigation from table reads + the
   session state alone. VERIFIED: choose is a pure, deterministic function of
   (position, history, table) with an explicit tie-break (`pick`: value →
   captures → DTT), so the mitigation can replicate the pick exactly. If the
   verdict were WRONG (search by default), "the move choose would return"
   would depend on search internals and A2 as specified collapses.
3. **"Both hold … play the extremum as today. No strength lost."** — relies on
   one-ply extremum == fresh-start-optimal on the chainable region
   (`GLOBAL.CHAIN-LH`, PROVEN). If choose did deeper search it could in
   principle beat the one-ply pick, and "no strength lost" would be false.
   VERIFIED keeps this line honest.
4. **Acceptance #2/#4** ("at the ply where the old engine played the −16
   child… refuses at ply 7 (not ply 8)") — the −16 child is the extremum's
   pick over incommensurable ko-sensitive children; reproducible from the table
   alone, so the regression can enumerate children and locate it. A searching
   choose would make the old pick unrecoverable from the table.
5. **Two wrinkles the H5a implementer must replicate** (exposed by reading the
   real body; the EXP-9 text mentions neither):
   - the **early-game override** (src/gtp.zig:208–224) can return `best_move`
     when pass is the extremum — `C*` is then a *non-extremum* move. A2's
     phrasing "the move choose would return" already covers this **provided the
     implementer reproduces the override**; checking only the extremum winner
     would leave overridden picks uncertified.
   - the **pass candidate** when `passes == 0` is priced by `v1_from_table`
     (a reconstructed V1, since the artifact stores V0 only). A1's "opt over
     children of `V0(child,-s)` == `V0(P,s)`" must decide how it treats the
     pass option; the chainability checker's ADR-0009 handling is the
     reference. One line in the H5a brief would forestall a mismatch.

Conclusion of calibration: **the H5a design's correctness depends on
`Session.choose` being a strict one-ply table extremum** in all four numbered
ways above, and the audited code is exactly that (with two documented policy
layers the implementer must mirror).
