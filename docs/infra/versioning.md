# Versioning

Every binary, artifact, and evidence file carries a version stamp so runs are
comparable across builds.

## Binary stamp

Every tool prints one version line on startup (stderr) and on `--version`:

```
weizigo-<tool> <sha>[-dirty] built <date> zig <ver>
```

Example:
```
weizigo-gtp e9f2165-dirty built 2026-08-02T00:54:30Z zig 0.16.0
```

The stamp is generated by `tools/gen-version.sh` at build time and embedded as
`src/version.zig` (gitignored). It records:

- `commit` — short git SHA from `git rev-parse --short HEAD`
- `dirty` — `true` if uncommitted changes were present at build time
  (staged **or** unstaged: `git diff --quiet && git diff --cached --quiet` —
  staged-but-uncommitted changes count, T268)
- `build_date` — UTC timestamp of the build
- `zig_version` — the Zig compiler version used (`zig version`)

**A dirty stamp on anything cited as evidence is a finding.** An artifact
built from uncommitted source is unreproducible.

Tools carrying the stamp: `weizigo`, `weizigo-gtp`, `verify-battery`,
`weizigo-oracle-v2-build`, `weizigo-claimlint`, `weizigo-absorb`, `managent`,
`weizigo-engine-vs-engine`, `weizigo-chainability`, `weizigo-reachcensus`.

## Version directories

Artifacts are stored in versioned directories under `untracked/`:

```
untracked/v01/
  oracle-4x4-v2.wzo2    ← the artifact
  manifest.json          ← producer provenance
  weizigo-oracle-v2-build ← the binary that built it (copy)
  weizigo-gtp            ← consumer binary (copy)
  ...
```

The counter `untracked/VERSION` holds the **next** version number. When a tool
produces an artifact, it:

1. Reads `untracked/VERSION` to get the current number N
2. Creates `untracked/v{N:0>2}/`
3. Writes the artifact and `manifest.json`
4. Copies the producing binary into the directory
5. Increments `untracked/VERSION` to N+1

A manifest records:

```json
{
  "tool": "weizigo-oracle-v2-build",
  "version": "weizigo-oracle-v2-build e9f2165-dirty built ...",
  "artifact": "oracle-4x4-v2.wzo2",
  "artifact_sha256": "a1b2c3...",
  "artifact_bytes": 42000000,
  "version_dir": "v01"
}
```

**This is a fresh scheme (T264, 2026-08-02).** No backward/forward
compatibility is designed yet. Each version directory is self-contained:
the binaries that produced and consume an artifact live next to it, so an old
version stays runnable for regression comparison.

## Evidence and findings

`verify-battery` includes the full version stamp in its JSON header as
`battery_version`. Every generated findings file records the version of the
tool that produced it.

For manually-authored findings JSON, record the version stamp of any tool
whose output is cited. Without this, a finding that "the battery says X" is
not comparable across runs.

## Comparing two runs

1. Check the version stamps are clean (no `-dirty`).
2. Check the git SHAs match — same source, same behaviour expected.
3. If SHAs differ, check `git log` between them for relevant changes.
4. Check the Zig versions match — different compiler versions can change
   floating-point or layout semantics.
5. For artifacts, compare `manifest.json` SHA-256 to ensure identical bytes.
