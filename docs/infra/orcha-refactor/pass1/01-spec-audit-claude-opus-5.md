## Questions (not findings — I could not settle these from the tree)

1. **Is C4 intended to anchor on a non-root member at all?** Finding 1 assumes the spec means what it says. If the intent is that the host guard anchors on `proc.pid` and the verb prunes to `largest_pid`'s subtree, the spec never says so and no arm covers it — but the defect would then be a wording defect rather than a design one.
2. **What determines "in-progress" for G6's protected set?** Run records are stamped at exit by `_finalize_run_record` (`tools/runner:1591`, `:1622`, `:1626`), so the presence-of-exit-fields test exists, but the spec never names it — and a SIGKILLed runner (`T548`'s case) leaves the record permanently unfinalized by design (`tools/runner:341-355`).
3. **Open question 3 (enumeration cost) is answerable now, cheaply**, without waiting for the design phase: `ps -axo pid= | wc -l` then a `python3` loop calling `os.getsid(p)` over that list, timed — the same shape as the §3 per-family script the spec already writes out. That measurement decides `sysctl(KERN_PROC_ALL)` versus `ps`+`getsid` before any code is written.
4. **Open question 6 is now closed, not open** — the GIVEN D10 measurement settles it at the kernel level. The consequence for the document is that the Provenance rejection line for B's token approach (`01-spec.md:438`) understates its own case: "its load-bearing readability claim is unverified" is now "disproven for any process but self on this host". I raise it as a note rather than a finding because the design does not rest on it either way.
